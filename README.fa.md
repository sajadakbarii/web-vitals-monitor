# Real User Web Vitals Monitor

[English](README.md) | **فارسی**

پایش سبک Core Web Vitals با داده‌ی کاربران واقعی (RUM) برای وردپرس، همراه با چک‌لیست رفع مشکل برای هر صفحه و دستیار هوش مصنوعی اختیاری.

این افزونه متریک‌های LCP، INP، CLS، FCP و TTFB را در مرورگر بازدیدکنندگان واقعی اندازه می‌گیرد، نتایج را در جدول‌های اختصاصی ذخیره می‌کند و در پیشخوان وردپرس بر اساس صدک 75 (P75) نمایش می‌دهد؛ یعنی همان روشی که Google Search Console برای ارزیابی به کار می‌برد. سپس از داده‌های Attribution بازدیدهای کند، راه‌حل‌های مشخص می‌سازد: پیشنهادهای کلی برای کل سایت، و یک چک‌لیست برای هر آدرس که دقیقاً می‌گوید کدام تصویر، المان، فایل یا تنظیم باید تغییر کند.

افزونه از کتابخانه‌ی رسمی [`web-vitals`](https://github.com/GoogleChrome/web-vitals) (نسخه‌ی 6.0.0، بیلد attribution) استفاده می‌کند که به‌صورت محلی در `assets/js/web-vitals.js` قرار دارد. به هیچ مرحله‌ی Build، CDN یا درخواست به سرویس شخص ثالث نیاز نیست.

## ویژگی‌های اصلی

- **تقریباً بدون هزینه برای سرعت سایت**: یک لودر درون‌خطی حدود 600 بایتی، نمونه‌برداری و فیلتر ربات‌ها را قبل از دانلود هر فایلی در مرورگر انجام می‌دهد و اسکریپت‌های جمع‌آوری را بعد از رویداد `load` و در زمان بیکاری مرورگر بارگذاری می‌کند. برای هر بازدید فقط یک درخواست ارسال می‌شود.
- **داده‌ی واقعی در P75**: ارزیابی Core Web Vitals (قبول / رد)، مقایسه با بازه‌ی قبل، توزیع خوب / نیازمند بهبود / ضعیف، و روند روزانه‌ی P75 با خطوط آستانه.
- **تفکیک**: فیلتر دستگاه (موبایل / تبلت / دسکتاپ) و فیلتر یک آدرس روی کل داشبورد اعمال می‌شوند؛ جدول‌های دستگاه، مرورگر و نوع صفحه.
- **پیشنهادهای بهینه‌سازی**: پیشنهادهای اولویت‌بندی‌شده برای کل سایت، بر اساس اجزای LCP، مراحل INP، زمان جابه‌جایی‌های چیدمان، تفکیک TTFB، تفاوت دستگاه‌ها، قالب‌های ضعیف و استفاده از bfcache و Prerender.
- **چک‌لیست اختصاصی هر صفحه**: برای هر آدرس مشکل‌دار، مشکلات از روی بازدیدهای خود همان صفحه شناسایی می‌شوند و هر مورد راه‌حل مخصوص خودش را دارد (نام واقعی فایل‌ها، سلکتورها، اندازه‌ها و تنظیمات افزونه‌ی بهینه‌سازی نصب‌شده روی سایت)، به‌همراه کد آماده‌ی کپی و بررسی نتیجه با بازدیدهای جدید پس از تیک زدن.
- **دستیار هوش مصنوعی (اختیاری)**: دکمه‌ی «پرسیدن از هوش مصنوعی» برای هر مورد چک‌لیست، با Claude API یا هر سرویس سازگار با OpenAI.
- **فارسی و راست‌به‌چپ (RTL)**: پیشنهادها، چک‌لیست و پاسخ‌های هوش مصنوعی به‌طور پیش‌فرض فارسی هستند، مستقل از زبان پیشخوان.
- خروجی CSV / JSON، مدت نگهداری داده، قوانین استثنا، تنظیمات حریم خصوصی و گزینه‌های حذف هنگام پاک کردن افزونه.

## پیش‌نیازها

- وردپرس 6.3 یا جدیدتر.
- PHP 8.1 یا جدیدتر؛ افزونه‌ی OpenSSL پیشنهاد می‌شود (برای رمزنگاری کلید API هوش مصنوعی).
- MySQL یا MariaDB در نسخه‌هایی که وردپرس فعلی پشتیبانی می‌کند.
- فقط برای دستیار هوش مصنوعی: دسترسی خروجی HTTPS از سرور به سرویس انتخاب‌شده (تنظیمات `WP_PROXY_*` وردپرس رعایت می‌شوند).

پشتیبانی مرورگرها به متریک بستگی دارد. LCP، FCP، TTFB و INP در نسخه‌های فعلی Chrome، Edge، Firefox و Safari اندازه‌گیری می‌شوند؛ CLS و دقیق‌ترین داده‌های Attribution (Long Animation Frames و فایل‌های مسدودکننده‌ی رندر) فقط از مرورگرهای مبتنی بر Chromium به دست می‌آیند.

## نصب

1. پوشه‌ی `web-vitals-monitor` را در `wp-content/plugins/` کپی کنید، یا فایل zip آن را از **افزونه‌ها ← افزودن ← بارگذاری افزونه** نصب کنید.
2. افزونه‌ی **Real User Web Vitals Monitor** را فعال کنید.
3. از منوی پیشخوان، **Web Vitals** را باز کنید.

بازدید مدیران به‌طور پیش‌فرض ثبت نمی‌شود؛ برای تست، سایت را بدون ورود یا در پنجره‌ی خصوصی (Private) باز کنید.

### به‌روزرسانی

- بعد از به‌روزرسانی، **کش صفحات را پاک کنید** تا صفحات کش‌شده لودر جدید را داشته باشند. آدرس اسکریپت‌ها شامل نسخه‌ی افزونه است، پس مرورگرها و CDN فایل‌های جدید را دریافت می‌کنند.
- به‌روزرسانی از نسخه‌ی 1.0، دیتابیس را در اولین بارگذاری یک صفحه‌ی پیشخوان مهاجرت می‌دهد: ردیف‌های تکراری CLS/INP (یک ردیف برای هر گزارشِ یک بازدید) یکی می‌شوند و ایندکس‌های بلااستفاده حذف می‌شوند. روی جدول‌های خیلی بزرگ، این اولین بارگذاری ممکن است کمی طول بکشد.

## داشبورد

**Web Vitals** در منوی پیشخوان، برای بازه‌ی انتخاب‌شده (24 ساعت، 7، 28 یا 90 روز) و دستگاه انتخاب‌شده این بخش‌ها را نشان می‌دهد:

| بخش | محتوا |
|---|---|
| ارزیابی | «قبول» وقتی LCP، INP و CLS همگی در P75 خوب باشند؛ در غیر این صورت «رد»، یا «داده‌ی کافی نیست» |
| کارت متریک‌ها | P75 با وضعیت، تغییر نسبت به بازه‌ی قبل، نوار توزیع، میانگین، میانه، P90 و تعداد نمونه |
| پیشنهادهای بهینه‌سازی | پیشنهادهای کلی سایت (وقتی یک آدرس انتخاب شده باشد مخفی می‌شود) |
| چک‌لیست اختصاصی صفحات | تا 10 آدرس بدتر، یا آدرس انتخاب‌شده، هر کدام با چک‌لیست مشکلات خودش |
| Performance Over Time | P75 روزانه‌ی LCP، INP و CLS با خطوط آستانه‌ی خوب / ضعیف |
| Performance Health | سهم تجربه‌های خوب (نیازمند بهبود نصف حساب می‌شود) و هشدارها |
| Top Problematic URLs | مرتب‌شده بر اساس تعداد نمونه‌های ضعیف؛ با کلیک روی هر آدرس، کل داشبورد به همان آدرس فیلتر می‌شود |
| Collector Health | وضعیت جمع‌آوری، آخرین نمونه، نمونه‌های امروز / کل، کرون، آخرین روز تجمیع‌شده |
| Device / Browser / Page type | P75 هر متریک Core Web Vitals برای هر دستگاه، مرورگر و نوع صفحه |

مقادیری که تعداد نمونه‌شان از حداقل تنظیم‌شده کمتر باشد «داده‌ی کافی نیست» نشان داده می‌شوند. داشبورد می‌تواند هر دقیقه خودکار به‌روز شود.

## پیشنهادهای بهینه‌سازی

پیشنهادها با قوانین ثابت در `includes/class-advisor.php` و بر اساس راهنمای web.dev ساخته می‌شوند، از داده‌های Attribution بازدیدهایی که در صدک 75 یا بالاتر هر متریک هستند:

- **LCP** به چهار جزء تقسیم می‌شود: TTFB، تأخیر شروع بارگذاری، مدت بارگذاری و تأخیر رندر. تصویر LCP با Lazy Load، نبود `fetchpriority`، تصویر اصلی به‌صورت بک‌گراند CSS، تصویر حجیم یا از دامنه‌ی دیگر، و تأخیر رندر شناسایی می‌شوند.
- **INP** به سه مرحله تقسیم می‌شود: تأخیر ورودی، پردازش و تأخیر نمایش. اسکریپت‌هایی که هنگام تعامل‌های کند اجرا می‌شدند به یک افزونه، قالب، هسته‌ی وردپرس یا یک دامنه‌ی شخص ثالث نسبت داده می‌شوند (با Long Animation Frames).
- **CLS** بر اساس زمان بزرگ‌ترین جابه‌جایی (هنگام یا بعد از بارگذاری) و نداشتن ابعاد برای رسانه تحلیل می‌شود.
- **TTFB** به ریدایرکت‌ها، DNS/اتصال و زمان سرور تفکیک می‌شود.
- تفاوت موبایل و دسکتاپ، قالب‌های صفحه با وضعیت ضعیف، امکان استفاده از Back/Forward Cache و Speculation Rules (پیش‌رندر) هم بررسی می‌شوند.

هر پیشنهاد شدت، شواهد از داده‌های خود سایت، مراحل رفع، آدرس‌های درگیر و لینک مستندات دارد.

## چک‌لیست اختصاصی صفحات

برای هر آدرس مشکل‌دار (10 آدرس با بیشترین نمونه‌ی ضعیف، یا آدرسی که انتخاب کرده‌اید)، `includes/class-page-issues.php` نمونه‌های خود همان صفحه را تحلیل می‌کند و فقط چیزی را به‌عنوان مشکل گزارش می‌کند که دست‌کم در 3 بازدید دیده شده باشد:

| مشکل | شرط شناسایی |
|---|---|
| Lazy Load روی تصویر LCP | تصویر LCP در 20% یا بیشتر بازدیدها `loading="lazy"` داشته باشد |
| تصویر LCP به‌صورت بک‌گراند | المان LCP بک‌گراند CSS باشد (وقتی LCP خوب نیست) |
| اولویت تصویر LCP | تأخیر شروع بارگذاری بیشتر از max(100 میلی‌ثانیه، 10% LCP) و بدون `fetchpriority="high"` |
| تصویر LCP بزرگ‌تر از نیاز | عرض واقعی دست‌کم 1.5 برابر عرض نمایش (بر حسب پیکسل دستگاه) و دست‌کم 300 پیکسل بیشتر |
| تصویر LCP حجیم | 150 کیلوبایت یا بیشتر (از 400 کیلوبایت به بعد همیشه گزارش می‌شود) |
| تصویر LCP از دامنه‌ی دیگر | بیشتر تصاویر LCP از دامنه‌ی دیگری بیایند و بارگذاری بیش از 30% LCP طول بکشد |
| نمایش دیرهنگام متن / المان | تأخیر رندر المان بیشتر از max(200 میلی‌ثانیه، 15% LCP) |
| فایل مسدودکننده‌ی رندر | یک فایل CSS یا اسکریپت در 30% یا بیشتر بازدیدها به مدت 80 میلی‌ثانیه یا بیشتر رندر را مسدود کند |
| پاسخ کند سرور | TTFB صفحه در P75 بیشتر از 800 میلی‌ثانیه (با TTFB کل سایت مقایسه می‌شود تا مشکل صفحه از مشکل سرور جدا شود) |
| تعامل کند | P75 بیشتر از 200 میلی‌ثانیه برای المانی که کاربران با آن تعامل می‌کنند (3 المان اول) |
| جابه‌جایی چیدمان | P75 بیشتر از 0.1 برای المانی که جابه‌جا می‌شود (3 المان اول) |

راه‌حل هر مورد مخصوص همان مشکل نوشته می‌شود: از نام فایل، سلکتور، اندازه یا ارتفاع اندازه‌گیری‌شده، مالک اسکریپت یا فایل CSS، و تنظیمات دقیق افزونه‌ی بهینه‌سازی فعال روی سایت استفاده می‌کند (WP Rocket، LiteSpeed Cache، Perfmatters، Smush، Autoptimize، a3 Lazy Load، W3 Total Cache، FlyingPress، Elementor). کدهای آماده (PHP برای قالب فرزند، CSS، JS یا یک دستور `curl`) از روی قالب‌های ثابت پر می‌شوند. داده‌های Attribution از یک endpoint عمومی می‌آیند، پس هر مقدار فقط وقتی داخل کد قرار می‌گیرد که از فهرست سفید کاراکترهای مجاز عبور کند؛ در غیر این صورت کد نمایش داده نمی‌شود.

**تیک زدن یک مورد** ذخیره می‌کند چه کسی و چه زمانی آن را تیک زده (بین همه‌ی مدیران مشترک است). نمونه‌هایی که بعد از آن جمع‌آوری می‌شوند دوباره بررسی می‌شوند:

- **رفع شد؛ بازدیدهای جدید تأیید کردند**: مشکل دیگر در دست‌کم 5 بازدید جدید دیده نمی‌شود.
- **هنوز مشاهده می‌شود**: بازدیدهای جدید هنوز همین مشکل را نشان می‌دهند.
- **در انتظار**: هنوز بازدید جدید کافی وجود ندارد.

## دستیار هوش مصنوعی (اختیاری)

برای هر مورد چک‌لیست یک دکمه‌ی **پرسیدن از هوش مصنوعی** اضافه می‌کند. مدل فقط همان یک مشکل را دریافت می‌کند و پاسخی ساختاریافته برمی‌گرداند: خلاصه، علت اصلی، مراحل به ترتیب، حداکثر یک قطعه کد، روش بررسی نتیجه، میزان اطمینان و موارد نامطمئن.

### راه‌اندازی

**Web Vitals ← Settings ← AI Assistant**:

| فیلد | توضیح |
|---|---|
| Enable AI suggestions | به‌طور پیش‌فرض خاموش است |
| Provider | **Claude (Anthropic API)** یا **OpenAI-compatible API** |
| API key | به‌صورت رمزنگاری‌شده ذخیره می‌شود؛ اگر خالی بماند کلید قبلی حفظ می‌شود |
| API address | برای Claude: خالی برای `https://api.anthropic.com`، یا آدرس یک رله. برای سرویس سازگار با OpenAI: الزامی، تا انتهای `/v1` (مثلاً `https://api.openai.com/v1` یا آدرس گیت‌وی). فقط HTTPS |
| Model | پیش‌فرض Claude: `claude-opus-5-5`؛ برای سرویس‌های سازگار با OpenAI، نام دقیق مدلی که سرویس‌دهنده اعلام کرده |

ذخیره کنید و سپس از **Test connection** استفاده کنید. به‌جای ذخیره‌ی کلید در دیتابیس، می‌توانید آن را در `wp-config.php` تعریف کنید:

```php
define( 'WVM_AI_API_KEY', 'your-api-key' );
```

### نحوه‌ی ارتباط با سرویس

- **Claude**: Messages API (`/v1/messages` با نسخه‌ی API `2026-10-21`) با خروجی JSON ساختاریافته (یک JSON schema ثابت) و `effort` برابر `medium`. پرامپت سیستمی که برای همه‌ی مشکلات یکسان است برای Prompt Caching علامت‌گذاری می‌شود. روی `api.anthropic.com` و با مدل‌های فعلی Opus، Sonnet 5.5 یا Fable، قابلیت Fallback سمت سرور فعال است؛ اگر یک فیلتر امنیتی درخواست را به‌اشتباه رد کند، روی مدل دیگری دوباره اجرا می‌شود.
- **سازگار با OpenAI**: Chat Completions (`/chat/completions`) با حالت JSON؛ ساختار پاسخ توسط خود افزونه بررسی می‌شود.
- درخواست‌ها از طریق WordPress HTTP API با زمان انتظار 180 ثانیه ارسال می‌شوند.

### داده، امنیت و هزینه

- **آنچه در هر درخواست ارسال می‌شود**: خود مشکل (عنوان، شواهد اندازه‌گیری‌شده، راه‌حل و کد قانون‌محور)، مسیر صفحه و مقادیر P75 آن، عنوان سایر مشکلات همان صفحه، نسخه‌ی وردپرس و PHP، و نام و نسخه‌ی قالب و افزونه‌های فعال. هیچ داده‌ای از بازدیدکنندگان، حساب‌های کاربری یا محتوا ارسال نمی‌شود.
- تا روی **پرسیدن از هوش مصنوعی** کلیک نکنید چیزی ارسال نمی‌شود. مرورگر فقط کلید مشکل را می‌فرستد و سرور خودش محتوای مشکل را دوباره می‌سازد.
- مقادیری که از مرورگر بازدیدکنندگان آمده‌اند (سلکتورها، آدرس‌ها) در پرامپت به‌عنوان داده برای تحلیل مشخص می‌شوند، نه دستور. خروجی هوش مصنوعی فقط به‌صورت متن نمایش داده می‌شود و کدها با هشدار «قبل از اعمال بررسی کنید» نشان داده می‌شوند؛ هیچ چیزی اجرا نمی‌شود.
- کلید API با AES-256-GCM و کلیدی که از Salt‌های سایت ساخته می‌شود رمزنگاری می‌شود، در گزینه‌ای ذخیره می‌شود که خودکار بارگذاری نمی‌شود، و دیگر هرگز نمایش داده نمی‌شود. تغییر Salt‌ها آن را نامعتبر می‌کند؛ در این صورت کلید را دوباره وارد کنید.
- پاسخ‌ها برای هر مشکل و مدل یک هفته کش می‌شوند (**پرسیدن دوباره** از کش عبور می‌کند). هر مدیر حداکثر 60 درخواست در ساعت می‌تواند ارسال کند.

## نحوه‌ی جمع‌آوری داده

1. در صفحات سایت که با الگوی آدرس مستثنا نشده‌اند، افزونه یک اسکریپت درون‌خطی کوچک (`wvm-loader`) همراه با تنظیماتش چاپ می‌کند.
2. در مرورگر، لودر نمونه‌برداری را اعمال می‌کند و ربات‌ها و User Agentهای مستثنا را کنار می‌گذارد؛ برای بقیه، `web-vitals.js` و `monitor.js` را بعد از `load` و در زمان بیکاری مرورگر (یا فوراً در حالت «Early») اضافه می‌کند. `web-vitals` ورودی‌های Performance بافرشده را می‌خواند، پس متریک‌های قبل از بارگذاری آن هم اندازه‌گیری می‌شوند.
3. `monitor.js` هر متریک را همراه با Attribution فشرده در صف می‌گذارد و وقتی صفحه مخفی شد، یک درخواست واحد می‌فرستد (`navigator.sendBeacon`، و در صورت نبود آن `fetch` با `keepalive`).
4. `POST /wp-json/web-vitals/v1/collect` داده را اعتبارسنجی و پاک‌سازی می‌کند، ربات‌ها را فیلتر می‌کند، محدودیت تعداد درخواست را اعمال می‌کند، وضعیت هر مقدار را تعیین می‌کند و آن را بر اساس شناسه‌ی متریک درج یا به‌روز (Upsert) می‌کند؛ بنابراین گزارش بعدیِ همان متریک (مثلاً CLS یا INP که بعد از برگشت کاربر به تب بزرگ‌تر شده) جایگزین گزارش قبلی می‌شود.
5. یک کار روزانه‌ی WP-Cron روزهای کامل‌شده را در جدول روزانه تجمیع می‌کند و ردیف‌های خام منقضی را حذف می‌کند.

داده‌های ثبت‌شده برای هر نمونه: متریک، مقدار، وضعیت، مسیر و نوع صفحه، نوع دستگاه (بر اساس عرض صفحه‌نمایش)، مرورگر و نسخه‌ی اصلی آن، سیستم‌عامل، نوع اتصال، ابعاد صفحه‌نمایش، نوع ناوبری، زبان، و Attribution فشرده (مثلاً المان LCP و اجزای آن، المان تعامل و مراحل آن، و المانی که جابه‌جا شده).

## REST API

فضای نام `web-vitals/v1`. Endpointهای مدیریتی به قابلیت `manage_options` و REST nonce نیاز دارند.

| متد | مسیر | کاربرد |
|---|---|---|
| POST | `/collect` | Endpoint عمومی جمع‌آوری |
| GET | `/dashboard` | داده‌های داشبورد (کش 60 ثانیه) |
| GET | `/suggestions` | پیشنهادهای کلی سایت (کش 10 دقیقه) |
| GET | `/page-issues` | چک‌لیست صفحات (کش 10 دقیقه) |
| POST | `/checklist` | تیک زدن یا برداشتن تیک یک مورد: `key` (16 کاراکتر هگز)، `done` |
| POST | `/ai-advice` | پاسخ هوش مصنوعی برای یک مشکل: `key`، `path` |
| GET | `/diagnostics` | بررسی فایل‌ها، Endpoint، دیتابیس و کرون |

Endpointهای گزارش، پارامترهای `days` (1 تا 90)، `device` (`mobile`، `tablet`، `desktop`)، `path` و `fresh=1` (عبور از کش) را می‌پذیرند.

`/collect` یک JSON حداکثر 16 کیلوبایتی با حداکثر 10 متریک می‌پذیرد، به شکل `{"c": {shared context}, "m": [metrics]}` (آرایه‌ی ساده‌ی نسخه‌ی 1.0 هم همچنان پذیرفته می‌شود). نام متریک‌ها و بازه‌ی مقادیر را بررسی می‌کند، شناسه‌ی متریک را الزامی می‌داند، فقط کلیدهای مجاز Attribution را نگه می‌دارد، Query String را از آدرس منابع حذف می‌کند و از Prepared Statement استفاده می‌کند.

## دیتابیس

جدول‌ها:

- `{prefix}web_vitals`: یک ردیف برای هر نمونه‌ی متریک. ایندکس‌ها: `UNIQUE (metric_id, metric_name)` برای Upsert، `created_at`، `(metric_name, created_at)`، `(url_hash, created_at)`.
- `{prefix}web_vitals_daily`: برای هر روز، متریک و دستگاه (`all`، `mobile`، `tablet`، `desktop`): مقادیر P50، P75، P90، تعداد هر وضعیت و تعداد نمونه.

گزینه‌ها (Options):

| گزینه | محتوا | بارگذاری خودکار |
|---|---|---|
| `wvm_settings` | تنظیمات | بله (در هر صفحه‌ی سایت خوانده می‌شود) |
| `wvm_db_version` | نسخه‌ی ساختار دیتابیس | بله |
| `wvm_checklist` | موارد تیک‌خورده‌ی چک‌لیست (حداکثر 1000) | خیر |
| `wvm_ai` | تنظیمات هوش مصنوعی و کلید رمزنگاری‌شده | خیر |
| `wvm_last_aggregated` | آخرین روز تجمیع‌شده | خیر |
| `wvm_cache_version` | نسخه‌ی کش گزارش‌ها | خیر |

Transientهای کوتاه‌مدت: `wvm_rl_*` (محدودیت درخواست، وقتی Object Cache وجود ندارد)، `wvm_dash_*`، `wvm_tips_*`، `wvm_pages_*` (کش گزارش‌ها)، `wvm_ai_*` (پاسخ‌ها و محدودیت‌های هوش مصنوعی).

## حریم خصوصی

- ذخیره نمی‌شوند: آدرس IP، نام، ایمیل، شناسه‌ی کاربر وردپرس، محتوای صفحه یا DOM. محدودیت درخواست از هش نمک‌دار IP در یک Transient استفاده می‌کند که ظرف چند دقیقه منقضی می‌شود.
- Query String به‌طور پیش‌فرض حذف می‌شود؛ آدرس منابع در Attribution هرگز Query String خود را نگه نمی‌دارند.
- مقادیر Attribution از فهرست مجاز انتخاب می‌شوند، پاک‌سازی می‌شوند و حداکثر 160 کاراکتر هستند.
- هیچ داده‌ای به شخص ثالث ارسال نمی‌شود، مگر به سرویس هوش مصنوعی انتخابی شما، آن هم وقتی یک مدیر روی **پرسیدن از هوش مصنوعی** کلیک کند (بخش [دستیار هوش مصنوعی](#دستیار-هوش-مصنوعی-اختیاری) را ببینید).

## کارایی

سمت سایت (Frontend):

- بدون jQuery، React یا کتابخانه‌ی نمودار؛ بدون درخواست به سرویس شخص ثالث.
- بازدیدکنندگانی که در نمونه نیستند و ربات‌ها چیزی جز لودر درون‌خطی دریافت نمی‌کنند.
- اسکریپت‌ها به‌طور پیش‌فرض بعد از `load` و در زمان بیکاری بارگذاری می‌شوند؛ یک درخواست برای هر بازدید و بدون تایمر.
- هیچ کوئری دیتابیس اضافه‌ای به صفحات سایت اضافه نمی‌شود (تنظیمات خودکار بارگذاری می‌شوند).
- تصمیم‌هایی که به هر بازدیدکننده بستگی دارند به HTML کش‌شده وابسته نیستند، پس پشت کش کامل صفحه هم درست کار می‌کنند: نمونه‌برداری در مرورگر انجام می‌شود و استثنای User Agent هم در مرورگر و هم دوباره در سرور.

سمت سرور:

- صدک‌ها از هیستوگرام‌های SQL محاسبه می‌شوند (بازه‌های 10 میلی‌ثانیه / 0.001 برای CLS در نمای کلی، و 25 میلی‌ثانیه / 0.005 برای جدول‌ها و روندها)، پس ردیف‌های خام هرگز در حافظه‌ی PHP بارگذاری نمی‌شوند.
- روندها از جدول روزانه خوانده می‌شوند؛ فقط روزهایی که هنوز تجمیع نشده‌اند از ردیف‌های خام محاسبه می‌شوند.
- برای هر درخواست جمع‌آوری فقط یک Insert چندردیفی.
- پاک‌سازی داده‌های قدیمی در دسته‌ها انجام می‌شود تا کامل شود یا 20 ثانیه بگذرد.
- محدودیت درخواست در صورت وجود از Object Cache دائمی استفاده می‌کند.

فایل `languages/web-vitals-monitor-fa_IR.po` ترجمه‌ی فارسی بخش‌های پیشنهادها، چک‌لیست و هوش مصنوعی است و منبع اصلی ترجمه محسوب می‌شود؛ `languages/web-vitals-monitor-fa_IR.mo` از روی آن ساخته می‌شود. بعد از ویرایش فایل `.po`، آن را با Poedit یا این دستور دوباره کامپایل کنید: `msgfmt -o web-vitals-monitor-fa_IR.mo web-vitals-monitor-fa_IR.po`. جای‌نگهدارها (`%s`، `%1$s`، `%%`) را تغییر ندهید و از ارقام لاتین استفاده کنید تا با اعدادی که از داده‌ها محاسبه می‌شوند یکسان باشند.

## رفع اشکال

داده‌ای ثبت نمی‌شود:

- مطمئن شوید پایش فعال است و نرخ نمونه‌برداری بیشتر از 0% است.
- بدون ورود به حساب یا در پنجره‌ی خصوصی تست کنید (بازدید مدیران به‌طور پیش‌فرض ثبت نمی‌شود).
- در تب Network مرورگر بررسی کنید که هنگام ترک یا مخفی کردن صفحه، یک درخواست POST به `/wp-json/web-vitals/v1/collect` ارسال می‌شود و پاسخ 201 برمی‌گرداند.
- مطمئن شوید افزونه‌ی امنیتی، فایروال یا CDN این درخواست POST را مسدود نمی‌کند.
- اگر افزونه‌ی بهینه‌سازی جاوااسکریپت اسکریپت‌ها را با تأخیر اجرا یا ترکیب می‌کند، اسکریپت درون‌خطی `wvm-loader`، `web-vitals.js` و `monitor.js` را از آن مستثنا کنید.
- بعد از به‌روزرسانی افزونه، کش صفحات را پاک کنید.
- بخش **Collector Health** در داشبورد زمان دریافت آخرین نمونه را نشان می‌دهد؛ `GET /wp-json/web-vitals/v1/diagnostics` فایل‌ها، Endpoint، جدول‌ها و کرون را بررسی می‌کند.

نمونه‌ها کم هستند: بازه‌ی زمانی را بزرگ‌تر کنید، نرخ نمونه‌برداری را بالا ببرید یا استثناها را کم کنید. INP فقط وقتی ثبت می‌شود که کاربر تعامل کند، پس طبیعی است نمونه‌های کمتری داشته باشد.

چک‌لیست خالی است: مشکلات به داده‌ی Attribution (به‌طور پیش‌فرض روشن) و دست‌کم 3 بار تکرار در همان صفحه نیاز دارند. برخی جزئیات مثل فهرست فایل‌های مسدودکننده‌ی رندر فقط در مرورگرهای مبتنی بر Chromium جمع‌آوری می‌شوند.

دستیار هوش مصنوعی:

- «کلید API پذیرفته نشد»: کلید را بررسی کنید و مطمئن شوید با سرویس انتخاب‌شده هم‌خوانی دارد.
- «آدرس یا نام مدل پیدا نشد»: آدرس API را بررسی کنید (آدرس سرویس‌های سازگار با OpenAI به `/v1` ختم می‌شود) و نام دقیق مدل را وارد کنید.
- «اتصال به سرویس هوش مصنوعی برقرار نشد»: سرور به آن دامنه دسترسی ندارد. از یک گیت‌وی یا رله‌ی در دسترس استفاده کنید، یا `WP_PROXY_HOST` / `WP_PROXY_PORT` را در `wp-config.php` تنظیم کنید.
- تغییر Salt‌های وردپرس کلید ذخیره‌شده را غیرقابل خواندن می‌کند؛ کلید را دوباره وارد کنید.

## تغییرات نسخه‌ها

### 1.4.0

- طراحی جدید داشبورد بر پایه‌ی یک دیزاین سیستم: توکن‌های رنگ با مقادیر روشن و تیره‌ی بررسی‌شده از نظر کنتراست، شکل برای هر وضعیت (دایره، مربع، مثلث) علاوه بر رنگ، نوار آستانه، نوار توزیع، نمودار روند P75 روی محدوده‌های خوب و ضعیف، و پراپرتی‌های منطقی CSS برای راست‌به‌چپ.
- جدید: بخش‌های «زمان LCP کجا صرف می‌شود» و «زمان INP کجا صرف می‌شود» برای یک آدرس (میانه‌ی اجزای LCP و مراحل INP در بازدیدهای کند همان صفحه).
- فونت‌ها روی خود افزونه هستند (حدود 185 کیلوبایت WOFF2 که فقط در صفحه‌های پیشخوان افزونه بارگذاری می‌شود) و داشبورد به هیچ CDN فونتی درخواست نمی‌دهد.
- بازه و دستگاه حالا دکمه‌های گروهی هستند و در هر مرورگر به خاطر سپرده می‌شوند؛ در چک‌لیست‌های طولانی 6 مورد اول نمایش داده می‌شود و بقیه با دکمه‌ی «نمایش بیشتر».

### 1.3.0

- جدید: دستیار هوش مصنوعی اختیاری برای موارد چک‌لیست (Settings ← AI Assistant)، با Claude API (مدل پیش‌فرض `claude-opus-5-5`، خروجی ساختاریافته، Fallback سمت سرور) یا هر سرویس سازگار با OpenAI. درخواست‌ها از WordPress HTTP API ارسال می‌شوند.
- کلید API هوش مصنوعی به‌صورت رمزنگاری‌شده در گزینه‌ای که خودکار بارگذاری نمی‌شود ذخیره می‌شود، دیگر نمایش داده نمی‌شود و می‌توان آن را به‌جای دیتابیس با `WVM_AI_API_KEY` در `wp-config.php` تعریف کرد.
- مشکلی که برای هوش مصنوعی ارسال می‌شود در سرور از روی کلیدش ساخته می‌شود؛ مقادیر آمده از بازدیدکنندگان در پرامپت فقط داده محسوب می‌شوند؛ کد هوش مصنوعی فقط به‌صورت متن و با هشدار بررسی نمایش داده می‌شود.

### 1.2.0

- جدید: چک‌لیست اختصاصی صفحات با راه‌حل مخصوص هر مشکل، دستورالعمل برای افزونه‌های بهینه‌سازی نصب‌شده، کدهای آماده و بررسی نتیجه با بازدیدهای جدید.
- Attribution جدید: عرض واقعی در برابر عرض نمایش و حجم تصویر LCP، فایل‌های مسدودکننده‌ی رندر صفحه، منبع و ارتفاع المانی که جابه‌جا می‌شود.
- کدهای آماده فقط مقادیر مجاز (از فهرست سفید) را شامل می‌شوند.

### 1.1.0

- جدید: پیشنهادهای بهینه‌سازی، فیلتر یک آدرس، فیلتر دستگاه، ارزیابی Core Web Vitals، مقایسه با بازه‌ی قبل، نوار توزیع، نمودار روند P75، تحلیل نوع صفحه.
- جدید: ترجمه‌ی فارسی بخش پیشنهادها.
- جدید: Attribution کامل‌تر (Lazy Load، اولویت دانلود، نوع و دامنه‌ی المان LCP؛ منبع اسکریپت INP از Long Animation Frames؛ رسانه‌ی بدون ابعاد در CLS).
- تنظیمات جدید: زمان بارگذاری جمع‌آوری‌کننده، محدودیت درخواست، اعتماد به هدرهای پروکسی. فرم خروجی با فیلتر؛ خروجی CSV/JSON به‌صورت جریانی.
- کارایی: لودر درون‌خطی با نمونه‌برداری در مرورگر، یک درخواست برای هر بازدید، بارگذاری خودکار تنظیمات، صدک با هیستوگرام SQL، ایندکس‌های سبک‌تر، Upsert دسته‌ای.
- رفع: CLS و INP برای هر گزارشِ یک بازدید دوباره ذخیره می‌شدند؛ ردیف‌های تکراری موجود هنگام به‌روزرسانی ادغام می‌شوند.
- رفع: امتیاز سلامت هرگز از 75 بالاتر نمی‌رفت؛ نمودار روند واحدها را با هم ترکیب می‌کرد؛ تقریباً همه‌ی آدرس‌ها مشکل‌دار علامت می‌خوردند.
- رفع: پاک‌سازی داده‌های قدیمی حداکثر 1000 ردیف در روز حذف می‌کرد؛ بازدیدکنندگان پشت CDN یک سهمیه‌ی محدودیت مشترک داشتند؛ استثنای User Agent پشت کش صفحه کار نمی‌کرد.
- رفع: آسیب‌پذیری Formula Injection در خروجی CSV.
